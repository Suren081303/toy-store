## Phase 6: Payments (done)
- Migration `Payments` applied: `Payments` table (one row per card payment attempt: provider, unique secret reference, amount, status Created/Paid/Failed/Cancelled, `NeedsRefund`) and bank details (`BankName`, `BankAccount`, `BankRecipient`) in `StoreSettings`. Placeholder bank details are seeded where empty ("Sample Bank", "AM00 ...", "Shop LLC").
- How card payment works here: checkout saves the order (Awaiting payment, stock reserved), `PaymentService` creates an attempt and the customer is sent to the bank's page. The bank's server sends a signed answer to `/{lang}/Payments/Callback`; only that answer changes the order. The page the customer returns to (`Payments/Return`) only reads the result from the database. The shop never sees card numbers.
- `IPaymentProvider` (Core) is the place for a real bank later. `FakePaymentProvider` + `/FakeBank` page (Pay / Decline / Cancel) exist only in Development and only while `Payments:Provider` = `Fake`; answers are signed with HMAC-SHA256 (`Payments:FakeSecret`, dev value in `appsettings.Development.json`). Without a provider, the card option is not shown.
- Answer rules: bad signature, wrong amount, or unknown reference change nothing (400/404 with a short text body); the same answer twice is handled once (emails sent once); a failed answer keeps the order waiting and "Pay now" starts a new attempt; a "paid" answer after the order was cancelled, or for an order already paid by another attempt, is stored with `NeedsRefund` and the order is not changed.
- Locking: status changes, payment answers, return requests and expiry use one per-order database lock (`DbLocks`), so a late payment and the expiry job cannot both win. `ChangeStatusAsync` has an `onlyIfCurrently` guard for this.
- Expiry job `PaymentExpiryService` (first run after 1 min, then every 5 min): cancels unpaid card orders after 30 min and bank-transfer orders after 3 days (`Payments:CardTimeoutMinutes`, `Payments:BankTransferTimeoutDays`) and puts the stock back.
- Bank transfer: order is saved as Awaiting payment; the confirmation page, order page and email show the bank details, the amount, "Order #N" as payment purpose and the pay-by time. `MarkBankTransferPaidAsync` (Awaiting -> Ordered, Paid) is ready for the admin button in Phase 7.
- Emails: card orders get the confirmation and the shop notice only after payment; cash and transfer orders right away. Emails are now written in the order's language even when the trigger is the bank's callback.
- Web: checkout offers cash / card (only with a provider) / bank transfer; order page and confirmation show "Pay now" for unpaid card orders; payment result page (failed, cancelled, waiting, expired, paid late). `OrderAccess` helper shared by orders and payments.
- Tests: 369 pass (new: deadline rules, fake bank signature checks, `PaymentService` on `ShopDb_OrderTests` including the same answer 5 times at once and expiry racing a paid answer, end-to-end card, failed/retry, cancelled, waiting, callback with good and forged signatures, bank transfer, Russian email).

## Phase 8: Notifications (done)
- Migration `Notifications` applied: `AdminNotifications` (the bell: type, order/return/product ids, amount, name, stock, read state) and `OutboxEmails` (the email queue: kind, order number, status Pending/Sent/Failed, attempts, next attempt, address, last error).
- Email queue ("outbox"): no email is sent while a request runs. The services write queue rows in the same transaction as the change that causes them (`NotificationWriter`), so an email is never lost between "saved" and "sent", and a mail outage never breaks an order. The email text is not stored: the sender makes it from the kind and the current order at send time (`OrderEmails.RenderAsync`). Emails are in the order's language; emails to the shop are in Armenian. Links are complete addresses built from the new setting `Shop:BaseUrl` (Development: http://localhost:5028; **production must set it**, otherwise the email fails with a clear error instead of going out with broken links).
- Sender job `EmailOutboxService` (first run 10 s after start, then every `Email:OutboxIntervalSeconds`, default 30, 5 in Development, 0 = off): takes due emails (20 per round), sends, saves the result. A failure is saved on the email (error text) and logged as an error, and it is tried again after 1, 5, 15, 60 minutes, 5 attempts in all; then it is "Failed" and shows on the dashboard ("Emails not sent") and on the Emails screen with a Retry button. One round at a time inside the site. Unlike the other jobs, an unexpected error in a round is logged and the next round still runs, so one hiccup cannot stop all email until a restart.
- Events: new order (cash/transfer when placed, card when paid) -> customer confirmation, shop notice, bell; return requested -> shop email + bell; payment that cannot be used -> shop email + bell "refund needed"; low stock (a product crosses 3 or fewer, once) -> bell only. Customer emails for: packed, delivered (with the return deadline), cancelled (by admin with the note, or "time to pay ran out"), bank transfer received, return rejected / goods received / money sent back (with the admin's note).
- Admin screens: bell in the admin header with the unread number, refreshed every 120 s while the page is visible (`/Admin/Notifications/Summary`, JSON, also puts "(n)" in the tab title); Notifications page (all / unread, Open marks read and goes to the order, return or product, Mark read, Mark all read; read state is shared between admins); Emails page (all / waiting / sent / failed, error text, Retry). Admin screens are in hy/ru/en.
- Clean-up job `NotificationCleanupService` (2 min after start, then daily): bell items older than 90 days, sent emails older than 30 days, failed emails older than 90 days. Waiting emails are never deleted.
- Old inline sending in `CheckoutController`, `PaymentsController` and `FakeBankController` was removed. Account emails (confirm email, reset password) are still sent directly: the person is waiting for them.

A copied path is never read from outside the uploads folder. The SKU must be new (case does not matter), 1-50 characters. Audit: `Product.Duplicated` ("NEW from OLD").
- **Change many products** (product list): tick products (a "select all" box for the page, needs the small script; the boxes belong to the bulk form by the `form` attribute, so the row forms are not nested), or choose "all N products that match the filter" when there is more than one page (up to 1000). Changes: set discount (0-100), change price by a percent (-90 to +1000, rounded to a whole dram, half up), set price, set stock (0-100000), hide (archive), show again, move to a category. **Always a preview first** (what each product has now -> after; products that already are like that; a problem such as a price below 1 or above 100 million), and nothing is saved until "Apply to N products". The apply gets the exact ids of the preview, checks everything again, and is **all or nothing** (one transaction, one lock, rows checked by their version: if an order or another admin changed a product meanwhile, nothing is saved and you are told). One audit line per changed product (`Product.Bulk`: "SetDiscount: 0 -> 20"); products that already were like that get none. After the change you come back to the same list (same filter; only an address on this site is accepted).
- **CSV export** (button, a POST because it writes an audit line `Export.Products`): every product including hidden ones, in the format of the import (`Sku, Brand, CategoryId, Price, DiscountPercent, Stock, Archived, NewArrival, NameHy, NameRu, NameEn, DescriptionHy, DescriptionRu, DescriptionEn, AgeGroupIds`; yes/no; age groups as `1;3`), UTF-8 with a byte-order mark, spreadsheet-safe (text starting with = + - @ gets an apostrophe, which the import removes again). A file exported and imported again changes nothing (tested, also with hard texts).
- **CSV import** (page "Import CSV": rules, a template to download, and the numbers of the categories and age groups, because the file uses numbers): the SKU is the key (known SKU = update, new SKU = new product). A column can be left out (not touched); an empty cell keeps the current value. A new product needs Brand, CategoryId, Price and NameHy, and stays **hidden unless the file says Archived = no**. Photos are not imported. Comma, semicolon or tab, quotes and line breaks inside quotes, a BOM, any case of the column names and SKUs. Up to 1000 rows and 2 MB. **Check first**: summary (create / update / no change), every problem by row and column (wrong number or range, unknown category or age group, a repeated SKU, text too long, a description without a name in that language, extra cells, unknown or repeated columns, empty file), and **nothing can be applied while any row has a problem**. "Apply the import" sends the file back, the server checks it again and saves everything in one transaction (one lock; two imports at once are handled one after the other). Audit: `Product.Imported` per created or changed product and one `Import.Products` summary.
